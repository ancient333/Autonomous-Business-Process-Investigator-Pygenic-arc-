# RootLens — Manufacturing / Industry 4.0

Opening line:
“Our project, RootLens, monitors a manufacturing workflow across Materials, Production and Quality stations. It records operations in PostgreSQL, detects database errors and unusual execution times, and investigates possible causes with supporting evidence.”

## One example to remember

A factory receives a production order for three steel brackets (product code BRACKET-1).

1. **Station A — Materials:** reserves six STEEL-BLANK units, using a simple demonstration bill of materials of two blanks per bracket. It writes materials_records.
2. **Station B — Production:** reads the reservation, computes three completed units, and writes production_records with a unique batch ID. This simulates the software record of fabrication, not physical machining.
3. **Station C — Quality:** reads the produced quantity, compares it with the requested three units, and stores the expected quantity, inspected quantity and pass/hold outcome in quality_records. It checks record consistency, not physical dimensions or defects.

A production order counts as completed only after a passing quality stage. Backlog/work in progress means all orders not yet quality-approved, including any quality holds.

## Your main incident demonstration

Click Start, collect 40 normal samples per worker, choose B / Production → LOCK TIMEOUT → Apply. The production worker performs a real bounded SQL lock wait on a dedicated demo record. It logs the actual PostgreSQL exception after rollback. Quality cannot finish the affected production order because Production has not completed it.

Say: “Quality is waiting on upstream Production; that does not automatically mean Quality is broken.”

Open the investigation and show the SQLSTATE, evidence IDs, affected production orders and incomplete stages. Click Recover; the condition clears, but the incident is only marked recovered after new healthy observations. Worker recovery does not certify every held batch as acceptable.

## Domain versus technology

| Question | Answer |
|---|---|
| Business domain | Manufacturing operations |
| Broader theme | Industry 4.0 / smart-manufacturing software |
| Problem | Finding where a production workflow is delayed and what the records support as a cause |
| ML | Per-worker Isolation Forest on historical execution durations |
| Investigation | Bounded rules comparing recorded evidence; no LLM planner |
| Connected machines | None; three independent local software workers represent stations |
| Source of orders | Synthetic production orders generated by the backend |
| Real operations | SQL reads/writes, transactions, durations, locks and exceptions |
| Not implemented | Physical machine control, PLC/IoT integration, defect imaging, predictive maintenance, finite stock depletion, OEE or scrap-rate estimation |

Do not present the earlier retail explanation. Use Materials/Production/Quality in both slides and the updated website. Do not call it predictive maintenance: no future equipment-failure prediction is implemented.
